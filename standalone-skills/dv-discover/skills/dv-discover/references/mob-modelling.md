# Mob Modelling & Profiling Questionnaire — Reference

Loaded by `/dv-discover` for context during discovery exercises and report generation.

---

## Mob Modelling Guidance

Mob modelling is a collaborative session where business stakeholders, data modellers, and engineers jointly identify vault constructs. Recommended for any discovery exercise where the business case isn't fully defined upfront.

**Establish the ubiquitous language first — polysemy and false cognates:**

- **Polysemy** — a single word carries multiple meanings depending on context. "Ticket" means different things in IT, airlines, retail. Hub names must be qualified if ambiguous across domains.
- **False cognates** — two people use the same term thinking they mean the same thing, but they don't. A business analyst says "account" meaning a contractual agreement; a developer hears "account" as a login credential. This is the most common source of modelling errors.

**Polysemes — shared entities across domains:**

A polyseme is a business concept that exists across multiple domains pointing to the same real-world entity. "Customer" in CRM and "customer" in billing = same entity, different attributes. Model as: one hub, multiple domain-specific satellites.

**Participant roles:**

| Role | Responsibility |
|---|---|
| **Subject Matter Expert** | Domain knowledge — ensures business logic is modelled correctly |
| **Technical Business Analyst** | Bridges business rules to source system representation |
| **Data Modeler (driver)** | Keeps session on track; captures decisions; controls the canvas |
| **Guardian** | Owns follow-up items that cannot be resolved during the session |

**Complementary techniques:** Domain Storytelling (pictographic language), Event Storming (sticky-note timeline). All produce vault-ready outputs: entity list with BKs, relationship map, unit-of-work definition.

## Data Profiling Questionnaire (pre-mob homework)

Assign to source-system SMEs before a mob modelling session. Answers feed directly into the profiling agents.

**Section A — Business Key Analysis (16 questions)**

| # | Question |
|---|---|
| A1 | What column(s) uniquely identify a single record in this table? |
| A2 | Is this key assigned by the business or generated by the system (surrogate)? |
| A3 | Can the key value change over time? (If yes → not a valid BK) |
| A4 | Is the key reused or recycled? |
| A5 | Does the key contain embedded meaning (smart key)? |
| A6 | Is the same key used in other systems? |
| A7 | Are there multiple key formats for the same entity? |
| A8 | Is case significant? |
| A9 | What is the key's data type and max length? |
| A10 | Are there known data quality issues with this key? |
| A11 | Is there a natural hierarchy? |
| A12 | Does the key depend on a parent key to be unique? (dep-child signal) |
| A13 | What is the business name for this identifier? |
| A14 | Is this key visible to end users / customers? |
| A15 | Is there an alternate key or cross-reference? |
| A16 | What is the expected key population growth rate? |

**Section B — Unit of Work (7 questions)**

| # | Question |
|---|---|
| B1 | What business event does this table record? |
| B2 | How many entities participate in one event? |
| B3 | Can the same combination appear more than once? |
| B4 | Is there a natural timestamp for when the event occurred? |
| B5 | Is this a point-in-time event or a relationship with a lifespan? |
| B6 | Can the relationship end and restart? (effectivity signal) |
| B7 | If one record were deleted, what business meaning would be lost? |

**Section C — Descriptive Content (10 questions)**

| # | Question |
|---|---|
| C1 | Which columns describe the entity vs. the relationship? |
| C2 | Which columns change frequently vs. rarely? |
| C3 | Are there columns always updated together? (split candidate) |
| C4 | Are there PII / sensitive columns? |
| C5 | Columns with multiple simultaneous values? (multi-active signal) |
| C6 | Columns overwritten without history? (non-historized signal) |
| C7 | Any columns derived or calculated? |
| C8 | What is the source of truth for each column group? |
| C9 | Columns that only apply to certain sub-types? |
| C10 | Expected volume of change per load cycle? |

**Section D — Peripheral (8 questions)**

| # | Question |
|---|---|
| D1 | Who is the business owner of this data? |
| D2 | Is there an existing data dictionary? |
| D3 | Known upstream dependencies? |
| D4 | Regulatory retention requirements? |
| D5 | Is this data replicated to other systems? |
| D6 | Known timing dependencies? |
| D7 | Is late-arriving data expected? |
| D8 | Are there soft deletes? |

**Usage:** Assign sections A-C as mandatory pre-session homework. Section D is collected during the mob session by the Guardian role.

## CDM / LDM / PDM in the data vault context

| Layer | Traditional | Data Vault approach | Priority |
|---|---|---|---|
| **CDM** | Design from scratch | Already derivable from business architecture. Hub tables ARE the conceptual model. | **Vital** |
| **LDM** | Full relational model | Source-system SME engagement surfaces CDEs and relationships. Link tables = logical relationships. | **Very important** |
| **PDM** | Define types, indexes | Source systems have already done this. Staging inherits the source's PDM. | **Important but not vital** |
